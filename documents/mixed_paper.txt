README.md

「このサイトで Noto Sans JP というフォントを使います」

そもそもフォントとは？

フォントは文字の見た目・書体です。

同じ「あいうえお」でも、

Noto Sans JP → ゴシック系の見た目
明朝体       → 明朝系の見た目

のように変わります。

Webサイトで Noto Sans JP を使いたければ、そのフォントのデータが必要です。

⸻

「ビルド時にフォントを取得」って？

例えば普通のWebサイトでは、Google Fontsを使うとき、ブラウザがGoogleのサーバーからフォントを取ってくる方式があります。

ユーザー
  ↓
あなたのWebサイトを開く
  ↓
HTML/CSSを取得
  ↓
ブラウザ
  ↓
Google Fontsにもアクセス
  ↓
Noto Sans JPをダウンロード

一方、Next.jsの next/font は、アプリをビルドするときにフォントを取得して、自分のWebサイト側に持たせます。

【ビルド時】
Next.js
   ↓
Noto Sans JPを取得
   ↓
自分のアプリに保存

そしてユーザーがアクセスしたときは、

【ユーザーのアクセス時】
ブラウザ
   ↓
あなたのWebサイト
   ├─ HTML
   ├─ CSS
   ├─ JS
   └─ フォント ← これも自分のサイトから配る

これがコメントにある self-host（セルフホスト） です。

フォントを外部から毎回取ってくるのではなく、自分のWebサイトから配信する

という意味です。

⸻

useActionState は何をするフックか

かなりざっくり言うと、

「フォーム送信で実行する関数の戻り値を、Reactのstateとして受け取れるようにするフック」

です。

今回だと、

const [state, formAction, isPending] =
  useActionState(createPost, initialState)

この1行で、

フォーム送信
   ↓
createPost が実行される
   ↓
createPost の return が
   ↓
state に入る
   ↓
再レンダリング

という流れを作ってくれます。

普通の useState に近い感覚もあります。

⸻

3つの戻り値

const [state, formAction, isPending] =
  useActionState(createPost, initialState)

それぞれこうです。

値	意味
state	Action が前回 return した値
formAction	<form action={...}> に渡す関数
isPending	今まさにAction実行中か

まず一番重要なのが state です。

最初は、

initialState = {}

なので、

state === {}

みたいな状態から始まります。

⸻

フォームを送信するとどうなるか

フォームがこうなっています。

<form action={formAction}>

ユーザーが送信すると、Reactが formAction を通して、最終的に

createPost(...)

を呼びます。

ただしここが普通の関数呼び出しと少し違います。

今回の createPost は、

export async function createPost(
  _prevState: CreatePostState,
  formData: FormData,
): Promise<CreatePostState>

ですよね。

引数が2つあります。

_prevState
formData

これは useActionState を使うと、Reactが自動的に渡してくれます。

つまりイメージとしてはReact内部で、

createPost(
  現在のstate,
  フォームのFormData,
)

と呼んでいる感じです。

⸻

具体例で見るとかなり分かりやすい

最初は、

state = {}

です。

そしてユーザーが、

タイトル: ""
slug: "hello"
本文: "こんにちは"

で送信したとします。

Reactはイメージとして、

createPost(
  {},
  formData,
)

を呼びます。

createPost の中で、

if (!title) {
  errors.title = 'タイトルを入力してください'
}

となります。

そして最終的に、

return {
  errors: {
    title: 'タイトルを入力してください'
  },
  values: {
    title: '',
    slug: 'hello',
    body: 'こんにちは'
  }
}

を返します。

すると、この戻り値がそのまま

state

になります。

つまり次のレンダリングでは、

state = {
  errors: {
    title: 'タイトルを入力してください'
  },
  values: {
    title: '',
    slug: 'hello',
    body: 'こんにちは'
  }
}

になっています。

なのでクライアント側では例えば、

{state.errors?.title && (
  <p>{state.errors.title}</p>
)}

とすれば、

タイトルを入力してください

を表示できます。

ここが useActionState の中心です。

⸻

useState と何が違うの？

普通なら例えば、

const [errors, setErrors] = useState({})

として、

const handleSubmit = async () => {
  const result = await createPost(...)
  setErrors(result.errors)
}

みたいなことを自分で書きそうですよね。

useActionState は、この

Action実行
↓
結果を受け取る
↓
stateを更新
↓
再レンダリング

をReactがまとめてやってくれます。

特にNext.jsの Server Action + form と非常に相性がいいです。

⸻

formAction は何なのか

これも重要です。

const [state, formAction, isPending] =
  useActionState(createPost, initialState)

ここで直接、

<form action={createPost}>

にはしていません。

代わりに、

<form action={formAction}>

です。

なぜかというと、useActionState が

createPost

を一枚ラップしているからです。

イメージすると、

const formAction = async (formData) => {
  const newState = await createPost(state, formData)
  // React内部でstate更新
  state = newState
}

みたいな役割です。

実際の内部実装はもちろん違いますが、理解としてはこれでかなり近いです。

だから、

<form action={formAction}>

とすることで、

フォーム送信結果をstateとして受け取れるようになる

わけです。

⸻

isPending はかなり単純

const [state, formAction, isPending] =
  useActionState(createPost, initialState)

isPending は、

送信していない
false
送信開始
true
Server Action実行中
true
処理終了
false

となります。

なので例えば、

<button disabled={isPending}>
  {isPending ? '投稿中...' : '投稿する'}
</button>

とできます。

ユーザーがボタンを連打するのを防げます。

⸻

今回のコード全体を一言で表すと

今回の、

const initialState: CreatePostState = {}
const [state, formAction, isPending] =
  useActionState(createPost, initialState)

は、

最初
state = {}
        ↓
<form action={formAction}>
        ↓
フォーム送信
        ↓
createPost(state, formData)
        ↓
return { errors, values }
        ↓
その戻り値が新しいstateになる
        ↓
画面にエラーを表示

という仕組みです。

特に覚えておくといいのは、

useActionState は「Actionの戻り値をReactのstateとして管理してくれるフック」

です。

そして今回 createPost の第1引数に突然

_prevState

が増えているのも、useActionState を使っているからです。普通に <form action={createPost}> とするだけなら、この引数の形にはなりません。

useState は「自分で state を変更する」
useActionState は「関数の実行結果で state が変更される」

という違いです。
========================
const [isPending, startTransition] = useTransition()

まず形としては、useState と似ています。

const [状態, 状態を変更する関数] = useState()

に対して、

const [isPending, startTransition] = useTransition()

は、

useTransition()
      ↓
┌─────────────────────────────┐
│ isPending                   │
│ → 処理中かどうか             │
│                             │
│ startTransition             │
│ → 処理をTransitionとして実行 │
└─────────────────────────────┘

という2つを返します。

たとえば検索でこう使います。

const [isPending, startTransition] = useTransition()
function search() {
  startTransition(() => {
    router.push('/blog?q=react')
  })
}

startTransition() の中に、

「この画面更新は緊急じゃないですよ」

という処理を入れます。

そして、その画面更新をReactが処理している間、

isPending === true

になります。

なので、

{isPending && <p>検索中...</p>}

みたいなことができます。

なんで普通に router.push() しないの？

ここが useTransition の本質です。

検索結果の更新などは、

入力操作などを邪魔してまで最優先で処理する必要はない

ですよね。

そこで、

startTransition(() => {
  router.push(...)
})

とすることでReactに、

「この更新は優先度低めの画面更新として扱ってね」

と伝えられます。

今回の検索フォームなら、おそらくこんな流れです。

検索ボックスに「react」と入力
        ↓
startTransition(() => {
  router.push('/blog?q=react')
})
        ↓
isPending = true
        ↓
BlogPageが新しいsearchParamsで更新される
        ↓
getPosts('react')
        ↓
検索結果が表示される
        ↓
isPending = false

なので今は、

useTransition() = 「ちょっと時間のかかる画面更新を行いつつ、その処理中かどうかも知るためのReact Hook」

くらいで覚えておけば十分です。

ちなみに isPending は「何らかの通信が全部終わるまで常にtrue」という汎用ローディング状態ではなく、そのTransitionによるReactの更新がPendingかどうかなのがポイントです。
